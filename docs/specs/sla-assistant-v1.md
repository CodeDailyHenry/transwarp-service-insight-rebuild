# SLA 智能诊断后端 V1 规格

## 1. 状态

- 状态：已确认
- 确认日期：2026-08-13
- 首个验收产品：ArgoDB
- 后续产品：Inceptor、HDFS、TCOS

## 2. 目标

为公司内部一线支持、交付和运维人员提供可信的多轮 SLA 诊断能力，让有明确知识依据的问题无需研发介入；不能可靠解决时，生成信息完整的研发升级摘要，减少研发追问和检索成本。

V1 与现有 SLA 机器人并行运行，先由管理员本人试用。V1 不以降低工单数字为唯一目标，优先保证答案有证据、适用范围明确且高风险操作受控。

## 3. 完成链路

```text
管理员导入资料
  -> 系统提炼候选知识
  -> 管理员审核并发布
  -> 使用者进入 CLI 诊断会话
  -> 自动或手动选择 ArgoDB 产品 Skill
  -> 检索、追问并形成诊断状态
  -> 输出带来源回答，或生成研发升级摘要
  -> 使用者反馈
  -> 固定历史问题集评测
```

只有整条链路跑通并达到第 13 节验收标准，V1 才算完成。

## 4. 角色与授权

| 角色 | 能力 |
| --- | --- |
| `user` | 问答、查看来源、提交反馈、提交候选知识 |
| `curator` | `user` 的全部能力，加上导入资料、提炼和编辑候选知识 |
| `admin` | `curator` 的全部能力，加上审核、发布、拒绝、撤回、回滚、重建索引、管理产品 Skill 和账号 |

首版只有初始维护者是 `admin`，新账号默认为 `user`。CLI 可以按角色隐藏管理帮助，但每个受限操作都必须由后端重新授权。

暂不接 SSO。部署时创建初始管理员和一次性个人令牌；服务端仅保存令牌哈希，明文只在创建或重置时展示一次。数据模型保留外部身份标识，以便以后接入 SSO 而不改变角色模型。

## 5. CLI 行为

执行 `sla ask` 创建新的诊断会话并进入 REPL。进程退出后再次执行会创建新会话；首版不恢复旧会话，但会保存脱敏的审计和评测记录。

支持以下会话命令：

| 命令 | 行为 |
| --- | --- |
| `/clear` | 清空对话摘要和诊断状态，开始新问题 |
| `/compact` | 压缩对话，同时保留结构化诊断状态 |
| `/skill <name>` | 选择并锁定主产品 Skill |
| `/auto` | 解除锁定并恢复自动路由 |
| `/sources` | 展示最近回答的完整来源 |
| `/context` | 展示当前诊断状态和对话摘要 |
| `/verbose on\|off` | 开关检索与路由调试信息 |
| `/feedback helpful\|unhelpful` | 反馈最近回答 |
| `/propose` | 将当前会话脱敏并提炼为候选知识 |
| `/help` | 按当前角色展示可用命令 |
| `/exit` | 退出当前会话 |

当估算上下文达到可配置阈值时自动执行压缩，并明确通知使用者。压缩结果必须同时包含自然语言摘要和结构化诊断状态，不得只依赖模型自由总结。

## 6. 产品 Skill 与诊断

产品 Skill 是可版本控制的目录，至少包含：

```text
skills/<skill-id>/
  SKILL.md
  metadata.yaml
  prompts/
  workflows/
  knowledge/
```

`metadata.yaml` 声明产品标识、别名、组件、支持的场景、关联 Skill 和版本。Markdown/YAML 承载常规知识与诊断规则；只有特殊解析或工具适配需要代码。

路由规则：

1. 使用者可以显式锁定产品 Skill。
2. 自动模式根据问题、诊断状态和产品别名产生带置信度的候选。
3. 置信度不足或候选接近时必须追问，不得静默误路由。
4. 跨产品问题使用一个主产品 Skill 和零到多个关联 Skill 检索。
5. 最终回答由一次统一诊断过程合并，不启动多个对话 Agent。

ArgoDB 是首个完整产品 Skill。Inceptor、HDFS 和 TCOS 在 V1 中只要求框架可扩展，不要求达到验收指标。

## 7. 知识导入与生命周期

首版通过本地文件导入 Markdown、TXT、PDF、Word、HTML，以及导出的 SLA JSON/CSV。暂不直接连接 Wiki 或 SLA 系统接口。

历史 SLA 聊天不得自动成为正式知识。系统先生成候选知识，管理员审核后才能发布：

```text
draft -> pending_review -> published -> deprecated
                       \-> rejected
```

每个知识版本至少记录：

- 稳定知识标识和不可变版本标识
- 产品、组件、问题类型和别名
- 适用产品版本、补丁和部署模式
- 正文、诊断步骤、风险等级和回滚信息
- 来源及来源定位
- 创建者、审核者、变更说明和时间
- 发布状态、有效期及替代版本
- 可见范围预留字段

正式问答只检索 `published` 版本。撤回和回滚产生审计事件，不原地改写历史版本。

来源冲突时按以下顺序处理：当前版本正式产品文档、已审核 SOP/知识条目、已确认解决的历史 SLA、普通 Wiki、未审核聊天记录。低优先级来源不得覆盖高优先级来源；无法消解时必须说明冲突并停止输出确定结论。

## 8. 检索与回答

检索采用可配置的混合方案：产品/版本等元数据过滤、关键词或稀疏检索、向量检索和重排。对话模型、Embedding 模型、Reranker 和知识提炼模型均通过独立接口配置，不绑定具体厂商或模型名称。

每轮诊断必须：

1. 从问题和已有诊断状态提取产品、组件、版本、环境、错误码和意图。
2. 判断是否需要追问关键条件。
3. 在主产品 Skill 内检索，必要时加入关联 Skill。
4. 基于来源优先级、版本适用性和相关度筛选证据。
5. 只依据选定证据生成回答。
6. 校验回答中的命令、配置项、版本范围和引用是否被证据支持。
7. 更新诊断状态并保存回答记录。

正常回答按需包含：直接结论、分析或对比、操作建议、适用版本及前置条件、风险提示、仍需信息和引用来源。默认中文并保留技术标识原文；主要使用英文提问时跟随英文回答。

默认只展示简短引用。详细模式额外展示 Skill 路由、检索词、检索范围、命中文档、相关度和未命中原因。调试信息必须来自真实检索轨迹，不允许由模型生成看似真实的命中记录。

## 9. 拒答与研发升级

以下情况必须追问、拒答或升级：

- 缺少会改变结论的版本或环境信息
- 没有足够的已发布证据
- 来源冲突无法消解
- 结论涉及未证实的命令、配置或版本能力
- 操作风险超过允许自动建议的级别

研发升级摘要包含产品、组件、版本、部署方式、环境、问题现象、错误码、关键日志、已尝试操作及结果、已检索知识、当前判断和未解决问题，并可直接复制到 SLA 工单。

## 10. 操作风险

| 风险 | 回答行为 |
| --- | --- |
| 低 | 给出操作步骤和来源 |
| 中 | 给出命令、前置检查、影响范围、验证和回滚方法 |
| 高 | 不给出可直接执行的破坏性命令，只给诊断建议和研发升级摘要 |

V1 不连接生产环境，也不自动执行 SQL、Shell、重启、删除或配置变更。

## 11. 后端模块及接口

V1 是 API-first 模块化单体。外部调用者只通过 HTTP 接口使用以下深模块；数据库、模型和索引细节不泄露到 CLI。

| 模块 | 核心接口职责 |
| --- | --- |
| Identity | 认证个人令牌、解析角色、管理账号和令牌 |
| Conversation | 创建会话、接收消息、清除或压缩上下文、读取诊断状态 |
| Diagnosis | 编排路由、追问、检索、证据校验、回答和升级摘要 |
| Skill Registry | 加载、校验和发布产品 Skill 定义 |
| Retrieval | 按检索请求返回可追溯证据，不暴露具体索引实现 |
| Knowledge | 导入来源、提炼候选知识、审核和管理不可变版本 |
| Feedback | 保存回答反馈和候选知识提议 |
| Evaluation | 对固定数据集运行可重复评测并生成指标 |
| Audit | 记录认证、知识变更和受限管理操作 |

建议的顶层 HTTP 资源：

```text
/v1/auth/*
/v1/sessions/*
/v1/skills/*
/v1/knowledge-sources/*
/v1/knowledge-candidates/*
/v1/knowledge-entries/*
/v1/feedback
/v1/evaluations/*
/v1/admin/users/*
/health/live
/health/ready
```

流式回答使用一种统一机制，优先采用 Server-Sent Events；非流式接口仍返回相同的最终回答模型。具体向量库、对象存储或模型调用由适配器实现，核心模块测试使用内存适配器。

## 12. 部署、存储与安全

V1 部署在内网 Linux 主机，通过 Docker Compose 运行：

- Python/FastAPI 后端
- PostgreSQL：业务数据、身份、权限、知识元数据和审计
- S3 兼容对象存储：原始资料和派生产物
- 可重建向量索引：混合检索数据
- OpenAI 兼容内网模型接口
- Redis：只有实际需要任务队列或缓存时才引入

CLI 使用 Python 实现，并作为纯 HTTP 客户端发布。后端和 CLI 的具体库版本在实现阶段锁定。

导入时识别并脱敏客户名称、IP、账号、令牌、凭证和其他敏感信息。原始资料、已发布知识和派生索引分开保存。查询、知识变更及管理员操作留存审计记录；日志不得记录明文令牌或完整敏感原文。

首版仅导入所有目标使用者均有权查看的资料。模型预留 `visibility`、`department` 和 `product_scope` 字段，但不实现复杂文档级权限。

系统不要求高可用，但持久化数据必须可备份恢复，向量索引必须能从正式知识重建。

## 13. 验收

从 ArgoDB 历史 SLA 中建立至少 50 至 100 个固定问题，保留期望 Skill、必要追问、参考答案、允许来源、风险级别和是否应升级等人工标注。

| 指标 | 门槛 |
| --- | ---: |
| 产品 Skill 路由正确率 | >= 90% |
| 引用来源正确率 | >= 95% |
| 有明确知识依据问题的答案可用率 | >= 80% |
| 无依据或版本不明问题的正确拒答/追问率 | >= 90% |

此外必须满足：

- 不编造命令、配置项或版本支持范围
- 高风险操作出现明确警告且不提供破坏性执行指令
- `/clear`、手动和自动 `/compact` 不串联无关问题
- `user` 和 `curator` 无法通过直接调用 HTTP 接口发布知识
- 已撤回知识不再被新回答检索
- 每个引用可定位到真实来源及其版本
- 核心回答经过管理员人工评审

## 14. V1 范围外

- Web 前端和外部客户访问
- SSO
- Wiki/SLA 系统实时连接器
- 复杂部门或文档级权限
- 知识图谱、MCP 和多智能体编排
- 自动执行生产操作
- 高可用集群
- 恢复历史 CLI 会话
- ArgoDB 之外产品的完整质量验收
